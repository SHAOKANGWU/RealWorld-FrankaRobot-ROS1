# Show-Harness on this ROS Panda

`scripts/show_harness.py` reproduces the paper's **single-arm zero-shot control
loop**, using your ROS observations and MoveIt. It is a standalone node with
its own observation validation, geometry helpers and execution methods; neither
policy imports or inherits from the other. The existing
`gpt_discrete_inference.py` remains the translation baseline. It already passed
a startup quaternion and raw finger positions to GPT; the new node turns these
into an evolving 6-DoF pose, measured gripper state and executable actions.

Sources: [paper, Sections 3 and Appendix 7.4](https://arxiv.org/pdf/2609.10522),
[authors' implementation](https://github.com/showlab/Show-Harness), and
[project page](https://showlab.github.io/Show-Harness/). This is a ROS adaptation,
not a port of the authors' entire stack or a claim of reproduced benchmark scores.

## Implemented interface

| Component | Implementation here |
| --- | --- |
| Perception | Every named RGB view from `MultiCameraSynchronizedObservation`, with camera-specific guidance |
| Proprioception | Measured `O_T_EE` position/quaternion, joints, named finger width, calibrated tip height, contact flags and external wrench |
| Planning | Separate VLM call producing ordered subgoals with visible completion criteria |
| Controller | VLM selects semantic units from current views, active subgoal and recent measured outcomes |
| Interpreter | Persistent Cartesian setpoint; calibrated semantic basis; base-frame rotation increments; workspace and tip-floor sweep rejection |
| Arm execution | MoveIt collision-checked Cartesian planning and execution through `position_joint_trajectory_controller` |
| Step selection | Fine when target is in wrist view; coarse otherwise; configurable fine-only ablation |
| Chunking | Bounded translation chunks when target is outside wrist view; each unit checks state and waits for settling |
| Gripper | Franka grasp/move actions; action result and fresh stable measured width |
| Recovery | Bounded automatic reopening and rollback to grasp stage after empty, unverified or lost grasp |
| Evaluation | ROS JSON events and optional exclusive-create JSONL trial file; summary script accepts independent success labels |

The movement alphabet is `MV_FWD`, `MV_BACK`, `MV_LEFT`, `MV_RIGHT`, `MV_UP`,
`MV_DOWN`, `ROTATE_CW`, `ROTATE_CCW`, `GRASP`, `RELEASE`, `DONE`.
`UNCERTAIN` is an additional stop outcome. Rotations include `axis: x/y/z`;
other actions use `axis: NONE`. `DONE` completes the **current subgoal**;
only the last subgoal ends the episode as `model_done`. These are model claims,
so independent task scoring remains separate.

Translation defaults are 2 cm fine and 4 cm coarse. Rotation defaults to 15°.
`semantic_to_base` columns specify forward, left and up in `panda_link0`.
Translation updates `x_next = x_setpoint + step * R * direction`; rotations
pre-multiply the current orientation about `R * axis`. CCW is positive
right-hand rotation, viewed toward the origin from the positive axis.
No numerical pose generated by GPT reaches the robot.

Structured output extends the paper's atomic contract to represent visibility,
chunks, rotation axis and confidence explicitly:

```json
{
  "actions": [{"action": "ROTATE_CCW", "axis": "z"}],
  "target_visible_in_wrist": true,
  "confidence": 0.9,
  "reasoning": "The fingers need to align with the object's long axis."
}
```

The node uses [Responses image inputs](https://developers.openai.com/api/docs/guides/images-vision)
and [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Each image is preceded by its camera name, frame and timestamp. The callback
caches observations; API and control work run in the main loop. Dry run invokes
the planner and one controller call, previews the chunk, and executes nothing.

The planner and controller instructions live in `planner_prompt` and
`controller_prompt` in `config/show_harness.yaml` as YAML multiline strings.
The node requires non-empty prompt strings and loads them at startup. Save
separate YAML configurations for prompt experiments and select one with
`config_file:=/path/to/config.yaml`; restarting the policy loads your edits.
The episode-start event records both actual prompts for reproducibility.
Action schemas, local response validation and motion limits remain in Python,
so editing a prompt does not change the executable action contract.

## Configure the rig

Edit `config/show_harness.yaml` and the receiver's camera configuration before
launching a trial. The supplied geometry and axis mapping are **examples**.

1. Match receiver camera names to `camera_guidance`; identify the reference
   and visibility views. Both roles may use the same camera. All configured
   cameras are required, and every timestamp is checked.
2. Calibrate the semantic table basis and describe how each action appears in
   each camera. The paper's image-direction rules belong to its rig; they are
   not copied blindly here. A wrist view changes when the end effector rotates.
3. Set the robot-base workspace box, measured `table_height`, and
   `tip_offset_ee` relative to **libfranka's configured EE frame**. The tip offset
   is not automatically relative to `panda_link8`. `F_T_EE` can already include
   a hand/tool offset. Do not count it twice. The zero default is valid only if
   the configured EE origin is the point whose clearance you want to enforce.
4. Set a vision/structured-output model available to your account. The shipped
   `gpt-5.6-terra` preserves your prototype setting; it is not an availability
   guarantee. Set reasoning effort only if the selected model supports it.
5. Tune gripper width thresholds, speed and force for the object and fingers.
   Width plus action success is a *holding candidate*, not proof of a grasp.

The floor protects the configured tip point, and the workspace protects the EE
origin. They are not full swept-volume collision checking. Contact/collision
flags and robot mode are monitored; unexpected motion or stale observations
end the run. A MoveIt step that fails to reach its target also ends the run
instead of accumulating more setpoint error.

## Start and preview

Use a ROS-compatible Python interpreter containing the SDK in `requirements.txt`.
The current workspace uses ROS Noetic/Python 3.8. Build to create node wrappers:

```bash
source /opt/ros/noetic/setup.bash
catkin_make
source devel/setup.bash
export OPENAI_API_KEY  # Set it through your usual environment/secret mechanism.
```

Start the real Panda MoveIt stack, camera drivers and receiver:

```bash
roslaunch panda_policy_inference startup_show_harness.launch robot_ip:=YOUR_ROBOT_IP
```

This launch starts `panda_moveit_config/franka_control.launch`, including
`move_group` and the Panda position trajectory controller. The policy sends
arm trajectories through MoveIt and owns synchronous standard Franka gripper
actions so it can verify their result.
Do not run keyboard teleoperation or another command publisher concurrently.
The current startup launch also starts two RealSense cameras using the serial
numbers configured in the launch file. It uses `show_harness_cameras.launch`
with RGB at 640 x 480 / 30 FPS; unused depth, infrared and point cloud streams
are off. Camera serials, `color_width`, `color_height`, `color_fps` and
`enable_depth` are launch arguments. Enable depth explicitly if another pipeline
needs it. The general observation receiver bringup is unchanged. The startup
does not move the robot to a begin pose; place it at a suitable stationary start
pose first.

Preview:

```bash
roslaunch panda_policy_inference show_harness.launch \
  task:='Pick up the red block and place it on the plate.' \
  dry_run:=true episode_log:=/tmp/show_preview_001.jsonl
```

If your SDK is installed in a virtual environment different from the catkin
wrapper's interpreter, use that environment's Python explicitly:

```bash
rosparam load src/panda_policy_inference/config/show_harness.yaml /show_harness
python3 src/panda_policy_inference/scripts/show_harness.py \
  _task_description:='Pick up the red block and place it on the plate.' \
  _dry_run:=true _episode_log:=/tmp/show_preview_002.jsonl
```

After verifying the calibrated configuration and preview, run with
`dry_run:=false` and a new log filename. No live robot or paid API call was used
to validate this implementation; first trials should be supervised.

MoveIt plans collision-checked Cartesian paths, converts EE targets through
`F_T_EE` to `panda_link8`, and checks the measured Franka pose against MoveIt.
Populate its planning scene with your table and fixtures. Show-Harness uses
MoveIt for all arm motions and does not switch controllers. The semantic VLM
interface remains the same, but this is an execution difference from the
paper's Franka impedance interpreter.

## Use only external camera2

The receiver and policy accept one RGB view plus robot and gripper state.
Use `camera2_only:=true` on both launches, in separate terminals:

```bash
roslaunch panda_policy_inference startup_show_harness.launch \
  robot_ip:=YOUR_ROBOT_IP camera2_only:=true
```

```bash
roslaunch panda_policy_inference show_harness.launch \
  camera2_only:=true task:='Move the robot end-effector above the green marker.' \
  dry_run:=true episode_log:=/tmp/show_camera2_preview_001.jsonl
```

Startup launches only camera2 and selects
`observation_receiver/config/camera2_observation_receiver.yaml`, so the
synchronizer waits only for camera2, robot state and gripper state. The policy
selects `config/show_harness_camera2.yaml`, with both `reference_camera` and
`wrist_camera` set to `camera2`, one camera guidance entry, and prompts that use
only the external view. The legacy `wrist_camera` and
`target_visible_in_wrist` names designate the visibility view; they do not
require a wrist-mounted camera. No image is duplicated for the two roles.

The single-camera YAMLs are separate trial profiles. If you change geometry,
calibration, model or other settings in the two-camera profiles, update the
single-camera profiles too. The camera2 guidance was copied from your current
rig conventions; review it if the camera or robot arrangement changes. You
can select other full profiles with `observation_config_file` on startup and
`config_file` on the policy launch.

With one RGB view, occlusion and out-of-image-plane alignment can be harder to
judge. Robot proprioception gives the EE pose but does not supply the marker's
3D location. The prompts request `UNCERTAIN` when the available view cannot
support an action or completion claim. Position the camera so the marker,
controlled gripper and vertical gap remain visible. The interpreter still
supports X/Y/Z, rotations and gripper actions. This is a single-view evaluation
variant of the paper's multiview setup; record that distinction in comparisons.

## Diagnose stale observations

`synchronized observation stream is not fresh` means the policy's latest
received observation exceeds `max_sensor_age` (currently 0.5 seconds).
Original timestamps for every camera, robot state and gripper state must also
meet that limit. The receiver requires all inputs within its `sync_slop`
window before publishing; any missing input or unmatched timestamps can cause
a gap even when the other topics are arriving.

At idle boundaries, including after GPT calls and MoveIt planning, the policy
waits up to `observation_timeout` (currently 10 seconds) for a valid fresh sample.
It issues no new action during this wait. GPT decisions retain their original
`max_decision_age` deadline, and robot pose/joint/gripper drift checks remain in
effect. Settling feedback and active gripper feedback keep strict freshness
checks. Increasing the idle wait does not permit older sensor data.

Restart the receiver and policy after updating these scripts. The receiver
prints health diagnostics every `diagnostic_period` seconds (default 5),
including each input's rate, receipt age and original timestamp age, plus the
synchronized output rate. Episode logs record `waiting_for_fresh_observation`,
`fresh_observation_resumed` and observation health on abort. Preview with
`dry_run:=true` and a new episode log before retrying live execution.

With ROS running, measure the output and suspect inputs in separate terminals:

```bash
rostopic hz /multi_camera_synchronized_observation
rostopic hz /camera1/color/image_raw
rostopic hz /camera2/color/image_raw
rostopic hz /franka_state_controller/franka_states
rostopic hz /franka_gripper/joint_states
```

If diagnostics identify a missing/stale input, check that driver, topic and
connection. A RealSense warning about USB 2.1 / reduced performance is a reason
to check the camera's USB 3 port and cable. Check the driver's reported USB type
after reconnecting; a USB 3-looking connector alone does not confirm the link
speed. The observed camera1 stalls also coincided with a depth stream start
failure. The Show-Harness camera launch disables that unused stream, but this
does not repair the USB connection. If all inputs are fresh but output
is stale, compare their header timestamps and synchronizer queue coverage.
Measure the skew before changing `sync_slop` or queue sizes; the policy still
enforces `max_sync_skew`. The publication log is throttled to once per second,
so its line frequency is not the actual topic rate. Keep the sensor-age limit
until the source of the delay is understood.

`chunks require a distant target and free-space translations` is a separate
decision validation error, before any action. The current contract requires
exactly one action when `target_visible_in_wrist` is true; only false permits
free-space translation chunks, excluding descent. Despite the legacy field
name, visibility refers to the configured `wrist_camera` (camera2 here, an
external view). The controller prompt and supplied `chunk_rule` spell out this
contract. Reload the policy YAML by restarting the policy after prompt edits.
Rejected proposals are retained as `model_response` events for evaluation.

## Evaluate repeated trials

Record `/show_harness/decision` and `/multi_camera_synchronized_observation`
with rosbag to retain the images. JSONL stores numerical state, plans,
decisions, proposed targets, actual outcomes, token usage, latency and terminal
status, but does not duplicate JPEGs. File creation is exclusive: use a unique
filename for every trial. `max_decisions` bounds controller queries;
`max_actions` separately bounds executed units including recovery opens.

Summarize logs without ROS:

```bash
python3 src/panda_policy_inference/scripts/evaluate_show_harness.py /tmp/trial_*.jsonl
```

Independently score recorded trials, then provide a JSON object keyed by the
episode IDs in the logs, for example `{"a_trial_episode_id": true}`:

```bash
python3 src/panda_policy_inference/scripts/evaluate_show_harness.py \
  /tmp/trial_*.jsonl --labels /tmp/success_labels.json
```

Dry runs are excluded from success and live-action averages. A model `DONE`
rate is reported separately from independently scored success. Reports include
termination reasons, action counts, recovery counts, horizontal reversals,
elapsed time, API latency and tokens. Reversals count successive horizontal
translations, with vertical/rotation/gripper events omitted from that metric.

Use the same task, initial poses, object arrangements and trial count for each
model. Keep geometry and MoveIt settings fixed. For plugin ablations, toggle
`subtask_planning`, `adaptive_step`, `action_chunking`, `failure_recovery`, or
`enable_rotation` in separate saved configs; set `fine_step_size: 0.01` to test
finer control. Record the configuration alongside the trial artifacts.

## Scope and checks

This implements the default zero-shot loop for one Panda. It does not implement
the optional visual-marker or situated-replanning plugins, video conditioning,
dual-arm control, GUMI demonstration collection, or LoRA training. The authors'
repository includes those additional workflows. This adaptation rejects unsafe
steps rather than clipping them, stops uncertain/low-confidence decisions,
disallows chunks containing descent, and requires measured pose settling after
each unit. These choices affect latency and make benchmark results non-identical.
RGB views and textual wrench/contact are supplied; no depth maps or tactile
images are added by this node.

Offline checks use generated ROS messages with mocked API/action/controller I/O:

```bash
source devel/setup.bash
/usr/bin/python3 -m unittest discover -s src/panda_policy_inference/tests -v
```
